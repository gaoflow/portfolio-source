我需要在一个已经拥有用户和稳定原生行为的 Android 产品中引入 React Native，而不是从头开发一个新应用。困难在于，混合集成会同时增加第二套运行时、打包路径和 UI 模型。如果边界没有划清，JavaScript 很快就会依赖 Android 的生命周期、线程、权限和构建细节，原有应用也会被拖入第二套架构。

我最终采用的边界是：原生代码继续掌握平台能力和恢复流程，Bridge 只提供范围有限、带版本的能力，React Native 管理自己的界面和页面状态。两套工具链最后接受同一套产品标准。

## 我先限制 React Native 的使用范围

我从输入、输出和导航都容易定义的界面着手，而不是让 React Native 直接接管与相机状态、音频处理、后台任务或自定义渲染深度耦合的部分。这些功能会扩大 Bridge，并迫使 JavaScript 理解大量 Android 生命周期假设。

适合混合集成的界面需要具备：

- 稳定的数据契约；
- 明确的进入和退出路径；
- 原生回退路径；
- 范围有限的平台操作；
- 双方一致的导航、返回值和错误定义。

React Native 可以管理自己的视图状态和呈现，但需要平台能力时，只能通过明确的操作请求原生模块。进入页面的导航、返回结果、分析指标的含义、无障碍支持和错误处理，也必须在原生端与 React Native 端采用相同定义。

缩小初始范围还有一个实际目的：只有这样，启动时间、交互表现、内存、包体成本和发布行为才容易比较。我没有把这些指标当成已经得到验证的结果，而是把它们保留为扩大集成范围前必须检查的条件。

## 我把 Bridge 设计成带版本的能力接口

我没有让 JavaScript 访问任意原生类。Bridge 只暴露少量操作，并使用可序列化的输入、明确的返回结果和有说明的线程行为。

接口关系可以概括为：

```text
JS feature → Capability v2 → Android adapter → platform API
           ← typed result / failure ←
```

线程切换、权限处理、Activity 回调和资源释放留在 Android 适配器中。React Native 只负责自己的渲染树和页面状态。如果每个 JavaScript 页面都需要理解 Activity 生命周期、线程切换和 Gradle 变体，说明 Bridge 并没有真正形成边界。

每次 Bridge 调用还必须带有版本假设。JavaScript bundle 和原生应用可能通过不同路径更新，动态分发时尤其如此。新的 bundle 不能假设每个已安装版本都已经包含某个原生方法。

为避免这种不兼容，原生宿主可以在启动时报告支持的操作或接口版本。JavaScript 根据能力选择兼容路径，并在用户触发不受支持的操作前拒绝该行为。Bridge 版本还需要写入发布清单，并进入运行时能力检查。

错误也必须以稳定类别跨越 Bridge。直接把原生堆栈跟踪交给 JavaScript，会泄露实现细节，也无法告诉界面应该重试、退出还是提示用户。我的边界设计是让原生适配器保留详细日志，只向 JavaScript 返回范围明确的错误类型和恢复操作。

## 每个生命周期状态只能有一个负责人

Android 负责进程、Activity、权限和许多外部回调；React Native 负责自己的渲染树和 JavaScript 状态。如果双方都认为自己负责同一个状态转换，功能就会变得不可靠。

权限请求是一个典型例子。JavaScript 可以请求某项能力，但平台对话框应由原生宿主协调，并且只把一次明确结果交给当前仍然有效的调用方。如果用户已经离开页面，或者宿主发生重建，这个请求必须按照预先定义的规则取消或重新连接。

身份验证、深层链接、推送通知和后台事件也遵循同一原则。原生代码先把平台事件转换成应用事件，等 React Native 界面准备好之后再交付。事件是暂存还是过期，只能由一个衔接面统一决定，不能由两边分别处理。

监听器的注册和清理也必须对称。如果 Bridge 留下一个已经废弃的 JavaScript 回调，它可能继续持有状态，并把事件传给已经不存在的界面。这类问题不是靠增加更多回调修复，而是靠明确所有权、失效条件和清理时机。

## 打包增加了新的兼容性问题

React Native 功能会增加 JavaScript、资源、原生依赖和构建配置。Android 构建产物现在必须证明这些部分彼此匹配。

与原生构建一起发布的 JavaScript 版本需要被记录。如果产品支持动态 bundle 更新，加载器必须验证：

- 签名；
- 目标原生版本；
- 文件完整性；
- 回滚状态。

JavaScript 更新可以改变生产环境行为，因此适用于原生热修复的控制也同样适用于动态 bundle。

原生依赖升级仍然必须通过应用商店发布。JavaScript 不能调用已安装二进制文件中不存在的原生能力。打包检查因此不能只验证 bundle，还要同时验证原生依赖、资源以及 JavaScript 与原生接口版本之间的映射。

包体大小和启动成本必须基于真实构建产物测量。我能确认完成了 React Native 集成，但现有信息没有说明迁移了哪些界面、bundle 增加了多大、性能发生了什么变化，也没有给出迁移比例。因此，这些内容是待验证的门槛，不是我已经取得的结果。

## 两套工具链必须遵守同一套完成标准

React Native 可以缩短某些 UI 的开发路径，但也会增加 JavaScript 测试、原生集成测试、依赖审查，以及跨两套运行时的调试工作。

我把完整功能需要检查的内容归为同一套标准：

- JavaScript 行为检查；
- 原生 Bridge 测试；
- 实际打包产物的冒烟测试；
- 无障碍审查；
- 失败路径验证；
- 进程或宿主重建后的恢复验证。

JavaScript 测试通过，并不能证明 Android 宿主能够加载 bundle，也不能证明功能能在进程重建后继续工作。相反，原生构建成功也不能证明 JavaScript 使用了兼容的能力版本。

职责归属应该跟随模块，而不是语言。修改混合功能的工程师需要对完整接口负责，包括 JavaScript 行为、原生行为和发布兼容性。

## 我能确认的结果和不能确认的结果

我完成了在成熟 Android 应用中的 React Native 集成。它没有把产品变成一个新应用，而是在原有系统中加入了第二套运行时、打包路径和 UI 模型。最终形成的可行边界很窄：Android 宿主保留平台控制权、兼容性和恢复能力，React Native 界面通过带版本的能力接口演进。

我没有可引用的数据来说明具体页面、bundle 大小、启动速度、内存变化、整体性能或迁移比例，也没有记录可以证明某次具体生产故障及其修复过程。因此，我不能把这些内容写成已经完成的优化或量化成果。

这次集成让我学会用一个简单问题判断跨平台边界的质量：调用方被迫理解多少原生知识？实用的模块会把大部分平台机制隐藏在小型能力接口之后；薄弱的集成则会把生命周期、线程、构建和版本细节暴露到各处。

目标从来不是抹去 Android，而是让边界明确的界面能够通过 React Native 演进。只有衔接面保持小范围、状态归属唯一、接口带版本、失败可以恢复时，混合模式才容易维护。缺少这些限制的 Bridge，会逐渐变成第二套应用架构，并渗漏到原有架构之中。
