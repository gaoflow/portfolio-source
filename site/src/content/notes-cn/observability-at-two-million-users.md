Lao You 的用户数超过了两百万。在这个规模下，即使一种故障只影响很小比例的用户，也会变成实际的支持问题。我面对的难题是：如果一种状况无法在自己的设备上复现，我们要怎样判断它发生在哪个版本、哪个状态转换和哪次操作中？

我能确认用户数已经超过两百万，但现有资料没有说明跨过这一门槛的时间，也没有记录具体事故、崩溃率或使用过的可观测性产品，所以我不会补写这些信息，也不会声称已经取得了无法证明的规模收益。

我的结论不是“记录一切”，而是建立一条尽量短的关联链：从用户可见的结果出发，补充解释代码路径所需的最小上下文，按版本和故障指纹聚合，再通过制品身份找到确切代码。用户名、消息正文、语音内容等用户数据不属于这条链。

## 先记录用户实际看到的结果

![移动可观测性关联链](/images/notes/systems/observability-at-two-million-users.svg)

崩溃容易观察，因为进程会意外终止。但许多代价高昂的故障不会造成崩溃，例如：

- 按钮一直处于禁用状态；
- 请求陷入循环；
- 礼物始终无法渲染；
- 登录状态与服务器不一致；
- 迁移过程悄无声息地丢失某项设置。

因此，我会先为重要流程定义明确的结果，例如已开始、已完成、已取消、已拒绝、已超时和已被取代。具体结果要根据操作本身决定。

只记录“已点击”和“错误”是不够的。这种做法会让中间过程消失，无法判断操作在哪一步停住。把日志散落在各个界面中也会带来问题：同一个事件可能被重复记录，后台路径却可能完全遗漏。

更合适的做法是在模块边界记录状态转换，因为决策在这里最明确。每次操作由一个明确的负责人记录一个终态结果，避免多个界面重复描述同一件事。

我还会使用稳定的操作 ID，把客户端的状态转换与后端处理关联起来，而不必在日志中保存请求负载或用户内容。

## 只保留能解释代码路径的上下文

一条诊断事件可以包含：

- 应用版本；
- 构建 ID；
- 操作系统版本；
- 设备类别；
- 功能配置；
- 相关模块状态；
- 操作 ID；
- 最终状态。

它通常不需要包含：

- 用户名；
- 消息正文；
- 语音样本或语音内容；
- 令牌；
- 完整的服务器响应。

这些关联键各自回答不同的问题：

| 关联键 | 回答的问题 |
|---|---|
| build ID | 哪一份代码产生？ |
| operation ID | 同一用户操作跨了哪些步骤？ |
| release cohort | 新版本是否偏离稳定基线？ |
| state transition | 卡在哪个转换？ |
| artifact hash | 符号和源码是否匹配？ |

我会尽量用范围有限的类别描述上下文。例如，连接结果可以分为离线、超时、身份验证、被拒绝、服务器、解析或已取消。自由格式的异常文本仍然有诊断价值，但稳定分类可以让不同版本之间的发生率具有可比性。

发布 ID 和热修复 ID 同样重要。即使两台设备安装的是同一个商店版本，也可能因为动态发布或热修复而运行不同的行为。激活之后生成的每一条事件，都应该带上当前生效的制品 ID。

移动应用还可能长时间离线。如果日志队列没有大小上限和保留期限，可观测性本身就会变成存储和性能问题。因此，队列必须同时限制容量和保存时间。

## 用聚合判断影响，而不是只看单条错误

一条堆栈跟踪只能描述一次故障。聚合之后，我才能看出多次故障是否集中在同一个指纹、应用版本、设备系列或发布状态上。

但崩溃分组不是诊断结论，只能作为初步假设：

- 如果没有保留符号映射，代码混淆会改变名称；
- 不同根本原因可能汇合到同一个框架堆栈帧；
- 同一个根本原因也可能产生多种堆栈。

我也不能只聚合崩溃。完成率、超时率、重复重试和状态转换违规，都可能揭示一个从不抛出异常、但实际上已经损坏的功能。

用户超过两百万以后，原始数量很容易误导判断。一个常见但无害的警告，其总数可能高于一次小规模新发布中的严重故障。因此，发生率需要选择合适的分母，例如：

- 活跃会话数；
- 尝试执行的操作数；
- 符合条件的设备数；
- 接触该功能的用户数。

两百万用户会让低概率故障影响大量真实用户，但由于现有资料没有具体事故和监控数据，我只能说明这种判断方法，不能给出实际改善数字。

## 发布判断必须有基线和停止条件

只有把当前指标与此前的稳定时期，或没有接触发布内容的用户群体进行比较，指标才真正具有行动价值。

发布记录需要标明制品进入每个发布阶段的时间。这样，我可以按制品比较崩溃和操作结果，而不是只按日历日期比较。

停止条件应该在发布前定义。否则，看到不利数据之后，团队很容易为糟糕的变更寻找理由，而不是按原先标准停止发布。

采样也不能一视同仁。常规成功事件可以采样，以控制成本。对于罕见的终态错误、完整性故障或与安全相关的状态转换，在隐私和成本限制允许的范围内，可能需要完整采集。

仪表板只有在负责人知道指标超过阈值后该做什么时才有用。如果没有明确行动，它只是一份可视化档案。

## 让每次诊断都能回到确切代码

有用的事件需要指出发生故障的模块和状态转换。源映射、符号文件、构建清单和制品哈希，则负责把运行时输出关联到确切代码。

有了这条路径，我才能使用受控的测试输入重建过程。目标是得到一个最小复现样例，或者形成一个边界明确的解释，而不是根据某一种设备型号猜测原因。

如果问题依赖陈旧数据或旧版本，修复点可能位于兼容性解析或服务器行为中，而不是最新的界面代码。操作 ID 和版本上下文可以让这种可能性一直可见。

一次诊断还应该反过来改进事件设计。如果调查中缺少某个类别、不变量或状态转换，我会补上这个缺口，让下一次调查更短。修正方法不是转储每一个本地对象，因为那会增加噪声、成本和隐私风险。

## 最终要观察软件，而不是用户

规模越大，收集更多数据的诱惑越强，错误选择带来的隐私代价也越高。

我更倾向于记录软件状态：制品、能力、状态转换、持续时间、结果类别，以及范围有限的设备上下文。敏感内容应该排除在常规遥测之外。只有在另有独立且明确的支持流程，并具备用户同意和保留期限控制时，才可能处理这些内容。

两百万用户让罕见的软件状态变得重要，但这不意味着每位用户的数据都可以被当作调试资源。对我来说，良好的移动端可观测性不是收集得更多，而是在减少数据收集的同时，把故障范围缩得更小。
