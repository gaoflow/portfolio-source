## 两百万用户先改变了判断

Lao You 的用户数超过了两百万。在这个规模下，哪怕一种故障只影响很小比例的用户，也会变成实际的支持问题。如果一种状况在我自己的设备上复现不出来，诊断就得回到它发生的版本、状态转换和具体操作。

我能确认用户数已经超过两百万。但现有资料没有说明跨过这一门槛的时间，也没有记录具体事故、崩溃率或使用过的可观测性产品。所以我不会补写这些信息，也不会声称自己已经取得了无法证明的规模收益。

我把范围收得很窄：从用户看得见的结果出发，只补上解释代码路径所需的最小上下文，按版本和故障指纹聚合，再通过制品身份找到确切代码。用户名、消息正文、语音内容这些用户数据，不属于这条链。

## 从用户看到的结果开始

![移动可观测性关联链](/images/notes/systems/observability-at-two-million-users.svg)

崩溃容易观察，因为进程会意外终止。但很多代价高昂的故障根本不会崩溃，比如：

- 按钮一直处于禁用状态；
- 请求陷入循环；
- 礼物始终渲染不出来；
- 登录状态与服务器不一致；
- 迁移过程悄无声息地丢了某项设置。

所以我会先为重要流程定义明确的结果，比如已开始、已完成、已取消、已拒绝、已超时和已被取代。具体结果要根据操作本身来定。

只记"已点击"和"错误"是不够的。这种做法会让中间过程消失，没法判断操作在哪一步停住了。把日志散落在各个界面里也会带来问题：同一个事件可能被重复记录，后台路径却可能完全漏掉。

更合适的做法是在模块边界记录状态转换，因为决策在这里最明确。每次操作由一个明确的负责人记录一个终态结果，避免多个界面重复描述同一件事。

我还会用稳定的操作 ID，把客户端的状态转换和后端处理关联起来，而不必在日志里保存请求负载或用户内容。

## 只留诊断需要的上下文

一条诊断事件可以包含：

- 应用版本；
- 构建 ID；
- 操作系统版本；
- 设备类别；
- 功能配置；
- 相关模块状态；
- 操作 ID；
- 最终状态。

它通常不需要包含：

- 用户名；
- 消息正文；
- 语音样本或语音内容；
- 令牌；
- 完整的服务器响应。

这些关联键各自回答不同的问题：

| 关联键 | 回答的问题 |
|---|---|
| build ID | 哪一份代码产生？ |
| operation ID | 同一用户操作跨了哪些步骤？ |
| release cohort | 新版本是否偏离稳定基线？ |
| state transition | 卡在哪个转换？ |
| artifact hash | 符号和源码是否匹配？ |

我会尽量用范围有限的类别去描述上下文。比如连接结果可以分成离线、超时、身份验证、被拒绝、服务器、解析或已取消。自由格式的异常文本仍然有诊断价值，但稳定分类能让不同版本之间的发生率具有可比性。

发布 ID 和热修复 ID 同样重要。哪怕两台设备安装的是同一个商店版本，也可能因为动态发布或热修复而运行着不同的行为。激活之后生成的每一条事件，都应该带上当前生效的制品 ID。

移动应用还可能长时间离线。如果日志队列没有大小上限和保留期限，可观测性自己就会变成存储和性能问题。所以队列必须同时限制容量和保存时间。

## 用聚合判断影响

一条堆栈跟踪只能描述一次故障。聚合之后，我才能看出来多次故障是不是集中在同一个指纹、应用版本、设备系列或发布状态上。

但崩溃分组不是诊断结论，只能当初步假设：

- 如果没有保留符号映射，代码混淆会改变名称；
- 不同的根本原因可能汇合到同一个框架堆栈帧；
- 同一个根本原因也可能产生好几种堆栈。

我也不能只聚合崩溃。完成率、超时率、重复重试和状态转换违规，都可能揭示一个从不抛异常、实际上已经坏掉的功能。

用户超过两百万以后，原始数量很容易误导判断。一个常见但无害的警告，总数可能高于一次小规模新发布里的严重故障。所以发生率得选对分母，比如：

- 活跃会话数；
- 尝试执行的操作数；
- 符合条件的设备数；
- 接触该功能的用户数。

两百万用户会让低概率故障影响大量真实用户。但由于现有资料没有保留下来的具体事故和监控数据，我只能说明这种判断方法，给不出实际改善数字。

## 发布前写好基线和停止条件

只有把当前指标和此前的稳定时期、或没有接触发布内容的用户群体进行比较，指标才真正有行动价值。

发布记录需要标明制品进入每个发布阶段的时间。这样我可以按制品比较崩溃和操作结果，而不是只按日历日期比。

停止条件应该在发布前就定义好。否则看到不利数据之后，团队很容易替糟糕的变更换理由，而不是按原先的标准停止发布。

采样也不能一视同仁。常规成功事件可以采样，用来控制成本。对于罕见的终态错误、完整性故障或与安全相关的状态转换，在隐私和成本限制允许的范围内，可能需要完整采集。

仪表板只有在负责人知道指标超过阈值后该做什么时才有用。没有明确行动的话，它只是一份可视化档案。

## 让诊断回到确切代码

有用的事件要能指出发生故障的模块和状态转换。源映射、符号文件、构建清单和制品哈希，负责把运行时输出关联到确切代码。

有了这条路径，我才能用受控的测试输入重建过程。目标是得到一个最小复现样例，或者形成一个边界明确的解释，而不是根据某一种设备型号猜原因。

如果问题依赖陈旧数据或旧版本，修复点可能在兼容性解析或服务器行为里，而不是最新的界面代码。操作 ID 和版本上下文能让这种可能性一直看得见。

一次诊断还应该反过来改进事件设计。如果调查里缺了某个类别、不变量或状态转换，我会把这个缺口补上，让下一次调查更短。修正方法不是转储每一个本地对象，因为那会增加噪声、成本和隐私风险。

## 观察软件，不观察用户

规模越大，收集更多数据的诱惑越强，错误选择带来的隐私代价也越高。

我更倾向于记录软件状态：制品、能力、状态转换、持续时间、结果类别，以及范围有限的设备上下文。敏感内容应该排除在常规遥测之外。只有在另有独立且明确的支持流程，并具备用户同意和保留期限控制时，才可能处理这些内容。

两百万用户让罕见的软件状态变得重要，但这不意味着每位用户的数据都能被当成调试资源。对我来说，可观测性的目标是在少收集用户数据的同时，把故障范围缩得更小。
