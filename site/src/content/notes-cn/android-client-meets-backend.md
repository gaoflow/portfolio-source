一个 API 只有在客户端能够根据响应做出正确决定时才算有用。有效 JSON 只是格式正确，Android 应用还需要知道应该重试、重新登录、保留缓存、显示部分结果还是停止操作。

我是从移动端开始接触后端，因此我一直用一个问题判断接口：这个响应能让应用下一步做什么？

![移动 API 决策接口](/images/notes/systems/android-client-meets-backend.svg)

## 失败也属于接口

超时、输入错误、身份过期和服务器错误不能都叫“网络失败”。

超时表示客户端不知道服务器是否完成；输入错误表示相同参数重试没有意义；身份过期可能需要刷新或登录；服务器错误也不能无限自动重试。

如果后端只给一个通用失败，界面就只能猜测。更好的做法是返回稳定的结果类别和客户端决策所需的最少信息，内部异常和数据库细节留在服务器。

## 登录不是一个布尔值

多个请求并发时，一个请求可能发现令牌过期，另一个仍在传输，第三个又在刷新完成前到达。

如果每个请求都自己刷新，就会出现竞态；刷新失败后仍保留旧凭据，应用会进入循环。

我把身份状态理解为已登录、刷新中、未登录和失败。具体名称不重要，关键是只能有一个组件负责状态转换，其他请求等待它的决定或明确失败。

## JSON 也有版本

移动客户端不会同时升级。服务器一次字段修改，可能要面对几个月甚至更久的旧版本。

增加可选字段通常比改变旧字段含义安全。删除枚举值、改变空值语义或复用字段，都可能保持 JSON 语法正确，却破坏旧客户端行为。

我会在网络边界把传输对象转换成应用内部值。解析器处理缺失字段和未知枚举，后面的界面与存储只使用稳定模型，不让原始 JSON 到处扩散。

这个转换层也方便直接输入旧版、当前版和缺字段载荷做测试。

## 写操作重试需要唯一标识

读取请求通常可以重试，写请求可能重复创建付款、消息、订单或礼物。

请求超时后，客户端不知道服务器是否已经提交操作。操作 ID 或幂等键需要在多次重试之间保持不变，服务器也必须识别它。

界面可以防止连续点击，但最终保证必须由服务器提供，因为只有服务器能看到全部已接受操作。

## 日志需要跨过客户端和服务器

客户端知道设备、应用版本、连接变化和最终界面状态；服务器知道请求处理、依赖、持久化和最终决定。

两边共享请求 ID 或操作 ID 后，可以追踪一次操作，不需要记录凭据或个人数据。没有标识时，只能对时间戳猜测。

## 先把响应变成有限结果

界面不应直接根据 HTTP 状态码拼行为。网络层先把响应转换为少量领域结果，状态机再决定下一步：

```kotlin
sealed interface SubmitResult {
  data class Accepted(val operationId: String) : SubmitResult
  data object Rejected : SubmitResult
  data object Reauthenticate : SubmitResult
  data class Unknown(val retryToken: String?) : SubmitResult
}
```

这段类型只用于说明接口思想，不声称 Lao You 使用了这些具体类名。

## 我保留的接口标准

后端应该提供最小且稳定的决策接口，客户端只转换一次，并明确处理成功、拒绝、身份变化和未知结果。

服务器框架和数据库可以更换，移动应用真正依赖的是在失败、延迟和版本变化中仍然稳定的含义。
