一个 API 算不算有用，要看客户端能不能拿着它的响应做出正确决定。返回一个合法 JSON 只说明格式没错；Android 应用真正需要知道的是：我该重试、该重新登录、该留着缓存、该显示部分结果，还是该停下来。

我是从移动端开始接触后端的，所以我判断一个接口的标准一直只有一个问题：这个响应能让应用下一步做什么？

![移动 API 决策接口](/images/notes/systems/android-client-meets-backend.svg)

## 为什么失败也是接口的一部分

超时、输入错误、身份过期、服务器错误，这几样不能统统叫“网络失败”。

超时的意思是客户端不知道服务器到底做没做完；输入错误的意思是拿同样参数重试没有意义；身份过期可能要刷新，也可能要重新登录；服务器错误也不能无限自动重试下去。

后端如果只扔回来一个笼统的“失败”，界面就只能猜。更好的做法是返回稳定的结果类别，外加客户端做决定需要的最少信息；内部异常和数据库细节留在服务器那边。

## 为什么登录不是一个布尔值

几个请求并发跑的时候，很容易出现这种场面：一个请求发现令牌过期了，另一个还在传输中，第三个在刷新完成之前又到了。

如果每个请求都自己去刷新，就会出现竞态；刷新失败了还把旧凭据留着，应用就会陷进循环里。

我把身份状态理解成几档：已登录、刷新中、未登录、失败。具体叫什么名字不重要，重要的是只能有一个组件负责状态转换，其他请求要么等它的决定，要么拿到一个明确的失败。

## JSON 也有版本

移动客户端不会同时升级。服务器改一次字段，可能要面对几个月甚至更久的旧版本。

一般来说，加可选字段比改变旧字段的含义安全。删掉枚举值、改变空值的语义、把字段拿来复用，这些操作 JSON 语法上都没错，却能把旧客户端的行为弄坏。

我的做法是在网络边界就把传输对象转换成应用内部的值。解析器负责处理缺失字段和不认识的枚举，后面的界面和存储只用稳定的模型，不让原始 JSON 到处扩散。

这个转换层还有一个好处：做测试的时候，可以直接拿旧版、当前版和缺字段的载荷往里喂。

## 为什么写操作重试要有唯一标识

读请求一般可以重试，写请求不一样：重试可能重复创建付款、消息、订单或者礼物。

请求超时之后，客户端根本不知道服务器是不是已经把操作提交了。所以操作 ID 或者幂等键要在多次重试之间保持不变，服务器也必须认得它。

界面上可以防连续点击，但最终的保证必须由服务器给出，因为只有服务器能看到全部已经接受的操作。

## 为什么日志要跨过客户端和服务器

客户端这边知道设备、应用版本、连接变化和最终的界面状态；服务器那边知道请求处理、依赖、持久化和最终决定。

两边共享一个请求 ID 或操作 ID 之后，一次操作就能从头追到尾，而且不需要记录凭据或个人数据。没有这个标识，排查时就只能对着时间戳猜。

## 我习惯先把响应变成有限的几种结果

界面不该直接拿 HTTP 状态码拼行为。网络层先把响应转换成少量几种领域结果，状态机再决定下一步：

```kotlin
sealed interface SubmitResult {
  data class Accepted(val operationId: String) : SubmitResult
  data object Rejected : SubmitResult
  data object Reauthenticate : SubmitResult
  data class Unknown(val retryToken: String?) : SubmitResult
}
```

这段类型只用来说明接口思想，不声称 Lao You 使用了这些具体类名。

## 我保留下来的接口标准

后端应该提供最小且稳定的决策接口；客户端只转换一次；成功、拒绝、身份变化和未知结果都要有明确处理。

服务器框架和数据库都可以换，移动应用真正依赖的，是在失败、延迟和版本变化中仍然稳定的那些含义。
