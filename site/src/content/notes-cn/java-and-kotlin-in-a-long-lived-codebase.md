## Java 和 Kotlin 共存

我的 Android 技术栈同时包含 Java 和 Kotlin。我关心的不是把一种语言全部换成另一种，而是避免两种语言对可空性、线程、错误和所有权作出不同的假设。

我能确认这两种语言都在我的技术栈里，但不能确认发生过正式的 Java 到 Kotlin 迁移，也确定不了迁移日期或范围。所以我不会虚构一条迁移时间线。这里讨论的是：一个长期维护的 Android 代码库，怎么让 Java 和 Kotlin 共存。

Kotlin 能改变代码表达规则的方式，但不能自动修复含义不清的状态、不安全的线程处理或过于宽泛的模块接口。我的核心判断是：两种语言必须共用同一套运行时、所有权、评审和发布规则。

## 写清 Java 与 Kotlin 的跨语言契约

![Java / Kotlin 共存契约](/images/notes/systems/java-and-kotlin-in-a-long-lived-codebase.svg)

我会先缩小语言边界，并在边界上把可空性、线程、错误和取消语义说清楚。性能判断则要落到实际生成的分配和调用上，不能只看源码是不是更短。

Java 和 Kotlin 会编译进同一个 Android 应用，但源码里的假设也会跨过语言边界。边界需要明确说明：

| 边界 | 需要声明 |
|---|---|
| 可空值 | 缺失原因与默认行为 |
| 异步调用 | 调度器、取消和所有者 |
| 集合 | 可变性与元素是否可空 |
| 异常 | 直接抛出、包装，还是使用结果类型 |
| 热点代码 | Lambda、装箱和临时集合分配 |

Java 方法如果没有可空性注解，可能返回 `null`。Kotlin 会把这种返回值当成平台类型，证明不了它安不安全，甚至可能绕过可空检查。直接把它当非空值用，失败只会被推迟。

我的修正方式是在语言边界设适配器：先验证输入，再返回显式的可空值、结果类型或已经成立的领域不变量。注解、结果类型和线程说明可以固定公共接口的语义，但不能拿来事后掩盖一个原本就没为两种语言共同设计的接口。

反过来，Kotlin 的默认参数、属性、扩展函数、伴生对象、受检异常行为、函数类型和协程，也可能把 Java 调用方看不见的约定带过边界。供两种语言共同使用的模块，得从一开始就面向双方调用者设计接口。

边界越窄，失败面越小。如果只有一个适配器负责跨语言交互，模块内部就可以各用各语言的惯用写法，也不必在多个层次之间反复转换 Java 和 Kotlin 模型。

## 不把所有缺失状态都压成 `null`

Kotlin 区分可空类型和非空类型，但类型本身解释不了一个值为什么缺失。

数据还没加载、服务器省略了字段、用户主动清掉了这个值、访问被禁止，这是四种不同的状态。如果全表示成 `null`，调用方只能自己猜下一步该等、该显示空值、该请求权限，还是该报错。

当行为依赖这些区别时，我会用密封结果或显式状态把含义留下来。对简单的可选数据，可空类型仍然合适。目标不是用复杂的类型层次替换掉每一个 `null`，而是让调用方能看清下一步决策。

`!!` 也代替不了语义。它表示程序员知道编译器不知道的信息，所以必须有局部证明。验证逻辑应该紧挨着断言，或者由能保证这个不变量的接口藏起来。否则所谓的空安全，只是把错误挪到了运行时。

## 给协程任务一个明确的所有者

协程让异步代码更好读，但也让人在没决定任务归属的时候就把工作启动了。

我把协程作用域看作生命周期和所有权声明：

- 界面相关的工作属于该界面或它的状态持有者。
- 应用级工作属于应用级所有者。
- 需要持久执行的后台工作，可能需要平台调度器和持久化输入，而不是只依赖内存中的作用域。

常见的失败是取消没有传递到阻塞或挂起操作。另一个失败是捕获宽泛异常后继续执行，把取消信号也一起吞掉。结果就是任务在它的所有者结束之后还活着。

修正方法是让取消沿调用链传递，并明确记录异步接口用的调度器、所有者和失败方式。

对于 Java 回调，我会把适配集中在一个边界，把回调转换成挂起函数。这个适配器要处理完成、错误、取消和重复回调保护。这样 Kotlin 调用方就能用结构化并发，而不必让 Java 回调机制遍布 Kotlin 代码。

## 用团队约束限制语言技巧

Kotlin 提供扩展函数、运算符重载、委托属性、内联函数和紧凑的表达式语法。这些特性都能澄清局部概念，但组合多了也会藏住控制流和内存分配。

为了让长期维护和评审更直接，我用这几条判断标准：

- 扩展函数应靠近它所阐明的类型和领域。
- 运算符应保留惯常含义。
- 作用域函数按可读性选，而不是按减少行数选。
- 公开模块接口应避免巧妙但复杂的泛型结构，免得每个调用方都要重新解读一遍。
- 状态所有权、错误含义、线程处理和发布行为，应在 Java 与 Kotlin 模块之间保持一致。

Java 代码也要遵守同样的标准。构建器、监听器、可变模型和静态辅助方法，都应该明确展示所有权和失败情况，不能依赖调用者熟悉某种惯例。

这些约定的实际结果，不是让代码看起来更"现代"，而是让工程师不用先在脑子里把各种语言技巧编译一遍，就能评审代码行为。

## 性能看实际分配和调用

源码短不等于运行时开销低。Lambda、集合操作、装箱、反射、委托属性和类型转换，都可能在热点路径里产生额外分配或重复工作。

我的处理原则是先测量，再把优化保持在局部：

- 让性能敏感的循环保持简单。
- 当某项语言特性的行为不确定时，检查生成后的实际行为。
- 避免在多个层次之间反复转换 Java 和 Kotlin 模型。
- 用一个适配器对数据做一次规范化处理，而不是在每个边界重复复制。

重复复制不只浪费内存，也会模糊数据所有权。

性能评审应该从可观测预算出发，比如启动时间、每帧工作量、内存或操作延迟，而不是在整个代码库里禁用某项语言特性。这里没有可用的测量数据能支撑具体性能数字，所以我不声称某种语言或写法天然更快。

## 共存仍有边界

只要模块对状态所有权、错误含义、线程处理和发布行为使用统一模型，Java 和 Kotlin 就可以在一个代码库里长期共存。

Kotlin 能让有效状态更容易表达，也能让异步路径更容易理解。Java 在稳定模块里仍然有可预测性和完整能力。重写只有在能消除具体风险或实现必要变更时才值得承担成本；语言更新本身不是充分理由。

这种做法的直接结果是：跨语言的不确定性只转换一次，调用方看到的契约更明确，模块内部也能保留各自语言的惯用约定。它的限制同样明确：这些规则不能自动解决业务状态定义错误，也替代不了性能测量、生命周期设计或代码评审。

到最后，我不再把问题归结为哪种语言更好。我保留了几个架构约束：跨语言接口保持精简，不确定性只转换一次，每个模块都说清自己的契约。
