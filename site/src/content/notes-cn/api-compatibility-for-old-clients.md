后端可以通过一次部署替换代码，但移动应用无法同时替换所有已安装的客户端。一次 Android API 变更往往要经历数月的兼容窗口。在这段时间里，新旧客户端会同时访问服务器，服务器也可能正在滚动部署不同版本。

我的移动端工作让我从客户端一侧理解了这个问题，我列出的后端技能则给了我描述服务器端问题的术语。我没有保留下某次 API 迁移的完整记录，因此不会把任何具体故障、修复或结果写成自己的经历。下面是我基于长期 Android 经验和后端技能总结的兼容性规则。

## 先看清新旧客户端必须共存多久

![旧客户端兼容窗口](/images/notes/systems/api-compatibility-for-old-clients.svg)

兼容窗口由已经部署的服务器和仍在使用的旧客户端共同决定。在退役字段或接口之前，我需要先定义新增语义、兼容默认值和能力检查，并找到能够证明旧调用方已经消失的数据。

我不会只问“新客户端能否调用新服务器”，而会检查过渡期内每一种受支持的组合能否正常工作：

- 旧客户端调用旧服务器；
- 旧客户端调用新服务器；
- 新客户端调用旧服务器；
- 新客户端调用新服务器；
- 同一端点背后同时运行不同版本的服务器。

这是一项双向工作：服务器要兼容缺少新字段的旧客户端，并决定如何处理新客户端发送的未知字段；客户端则要处理响应字段缺失、枚举扩展和能力关闭。

## 增加字段不等于保持兼容

相对安全的 API 变更，是增加客户端可以理解的内容，同时不改变现有内容的含义。例如，旧客户端通常可以忽略可选的响应字段，但这并不代表所有增量变更都安全。

以下变化都可能让旧客户端失败：

- 新的枚举值可能被旧解析器拒绝，或落入错误的默认分支；
- 字段从缺失变为 `null`，可能改变界面行为；
- 字段从 `null` 变为空值，也可能改变界面行为；
- 改变旧字段的含义，即使传输格式不变，也会破坏原有契约；
- 旧客户端可能无法处理重复值、超出预期范围的值或未知值。

因此，我会逐个考虑字段在缺失、未知、为空、重复或大于预期时会发生什么。JSON 仍然有效，只能说明传输层格式正确，不能说明应用行为仍然正确。

在 Android 上，我认为这些决定应该集中在传输适配器中。未知值应转换成明确的 `Unknown` 状态，或一个边界清楚的回退值。原始的服务器枚举不应该直接扩散到各个界面，否则每项功能都可能形成不同的默认行为。

## 请求字段也必须逐步演进

兼容问题不只存在于响应中。新客户端可能会向旧后端发送无法识别的字段；在服务器滚动部署期间，同一个端点背后也可能同时运行不同版本。

请求解析器应该筛选可接受的输入，并拒绝有歧义的内容。如果服务器默默接受一个自己会忽略的字段，客户端可能误以为这个字段已经影响了操作结果。当某项不受支持的能力会改变结果时，响应应该明确说明该能力没有生效。

新增请求字段时，服务器可以通过默认值兼容旧客户端，但这个默认值必须与旧客户端原来的行为一致。如果借默认值引入新策略，就会在没有提示的情况下改变现有应用的行为。新增字段也不应立即设为必填。

写操作还要考虑重试。如果请求超时后重试会让同一个操作执行两次，那么即使字段和版本都兼容，结果仍然不可靠。因此，可能产生重复效果的写操作需要具备幂等性，并使用能够识别同一操作的标识。

## 只有契约真正不兼容时才增加版本

带版本号的路径可以隔离不兼容的契约，但也会产生多套需要维护、监控和退役的接口。

如果可选字段、默认值和未知值都经过清楚设计，小规模的增量变更通常可以留在同一个版本中。只有当资源含义、授权模型或操作语义发生了足够大的变化，已经很难解释新旧行为如何在同一契约中共存时，新版本才值得承担这些成本。

客户端版本号只能作为较弱的能力信号。两个构建版本可能属于同一个版本系列，却因为平台、发布批次或配置而具有不同能力。如果功能依赖某种具体行为，显式的能力握手通常比维护庞大的版本比较表更清楚。

服务器仍应记录应用版本，用于诊断问题和判断退役条件，但不能信任客户端提供的版本值来做安全决策。

## 功能开关必须有安全的关闭状态

功能开关可以在不等待应用更新的情况下停止新行为，但前提是每个活跃客户端在开关打开和关闭时都能正常工作。

关闭状态需要同时定义界面结果和数据行为。例如：

- 如果关闭写入路径，却让缓存中的控件继续显示，用户只会反复遇到失败；
- 如果移除响应对象，而旧客户端假定该对象一定存在，应用可能崩溃；
- 如果能力不可用，客户端需要能够显示明确的替代状态，而不是继续尝试不可能成功的操作。

每个功能开关都应该写明适用对象、默认值、回滚行为、负责人、过期时间和移除条件。永久存在并彼此重叠的开关，会逐渐形成一组无人能够完整说清的契约。

服务器控制的开关也不能取代客户端保护。应用仍然要处理能力缺失、操作被拒绝和缓存状态过期等情况。

## 删除旧契约前要证明调用方已经消失

我不能只根据发布时间或下载量判断旧客户端是否已经退出。下载量不能证明实际活跃使用情况，发布时间也不能说明所有用户已经更新。

服务器记录可以显示不同应用版本对各端点的请求情况。测量窗口需要足够长，以覆盖不频繁使用应用的用户；用于统计的标识符也必须顾及隐私。

只有在旧契约的调用方已经消失，或业务明确决定接受剩余影响时，才能移除它。退役应按以下顺序进行：

1. 停止创建对旧契约的新依赖；
2. 在适当情况下公布支持边界；
3. 衡量旧路径的剩余流量；
4. 以可控方式拒绝或重定向请求；
5. 确认旧路径不再有流量；
6. 移除服务器端的兼容代码。

客户端也要清理不再使用的解析器、功能开关和回退分支。只要它们已经不再服务任何活跃版本，就应该移除。没有退役规则的兼容代码最终会变成永久的歧义。

## 我把 API 变更看成双方共同维护的状态

API 是服务器部署和已安装应用之间的共享状态，任何一方都不能单独改变自己对它的解释。

后端需要提供稳定的语义、兼容的默认值和可以衡量的退役过程。Android 客户端需要宽容地解析响应，明确表示未知状态，并提供安全的回退。双方都需要操作标识和可用于诊断的版本信息。

这改变了我评估 API 变更的方式：重点不只是新客户端与新服务器能否达成一致，而是过渡期间每一种受支持的组合能否继续做出正确决定。版本号和功能开关只是工具；真正决定兼容性的，是字段含义、默认行为、能力检查、幂等性以及有证据支持的退役规则。
