## 这篇只写长期形成的规则

后端部署一次，代码就全换了。移动应用做不到这一点：装在用户手机上的客户端，我不可能同时全部换掉。一次 Android API 变更，往往要经历数月的兼容窗口。这段时间里，新旧客户端同时在访问服务器，服务器自己也可能正在滚动部署不同版本。

我做移动端的工作，让我从客户端一侧理解了这个问题；我列出的后端技能，又给了我描述服务器端问题的术语。我没有保留下某次 API 迁移的完整记录，所以我不会把任何具体故障、修复或结果写成自己的经历。下面写的，是我基于长期 Android 经验和后端技能总结出来的兼容性规则。

## 先确定新旧客户端的共存窗口

![旧客户端兼容窗口](/images/notes/systems/api-compatibility-for-old-clients.svg)

兼容窗口是两头一起决定的：一头是已经部署的服务器，另一头是还在用的旧客户端。在退役一个字段或接口之前，我要先定义好新增语义、兼容默认值和能力检查，还要找到能证明旧调用方已经消失的数据。

我不会只问“新客户端能不能调用新服务器”。我会把过渡期里每一种受支持的组合都检查一遍：

- 旧客户端调用旧服务器；
- 旧客户端调用新服务器；
- 新客户端调用旧服务器；
- 新客户端调用新服务器；
- 同一端点背后同时跑着不同版本的服务器。

这是双向的工作。服务器要兼容缺少新字段的旧客户端，还要决定怎么处理新客户端发来的未知字段；客户端则要处理响应字段缺失、枚举扩展和能力被关掉这些情况。

## 增量字段也可能破坏旧行为

相对安全的 API 变更，是增加客户端能理解的内容，同时不改变现有内容的含义。比如旧客户端通常可以忽略可选的响应字段。但这不代表所有增量变更都安全。

下面这几种变化，都可能让旧客户端失败：

- 新的枚举值可能被旧解析器拒绝，或者掉进错误的默认分支；
- 字段从缺失变成 `null`，可能改变界面行为；
- 字段从 `null` 变成空值，也可能改变界面行为；
- 改变旧字段的含义，即使传输格式不变，也破坏了原有契约；
- 旧客户端可能处理不了重复值、超出预期范围的值或未知值。

所以我会逐个字段去想：它缺失、未知、为空、重复、比预期大的时候，分别会发生什么。JSON 仍然有效，只说明传输层格式是对的，说明不了应用行为还是对的。

在 Android 上，我认为这些决定应该集中在传输适配器里做。未知值要转成明确的 `Unknown` 状态，或者一个边界清楚的回退值。原始的服务器枚举不应该直接扩散到各个界面，不然每项功能都会长出自己一套默认行为。

## 请求字段也要渐进演进

兼容问题不只在响应里。新客户端可能向旧后端发送它不认得的字段；服务器滚动部署期间，同一个端点背后也可能同时跑着不同版本。

请求解析器应该筛选能接受的输入，拒绝有歧义的内容。如果服务器默默接受一个自己会忽略的字段，客户端可能误以为这个字段已经影响了操作结果。当某项不受支持的能力会改变结果时，响应应该明确说这个能力没有生效。

新增请求字段时，服务器可以用默认值兼容旧客户端，但这个默认值必须跟旧客户端原来的行为一致。要是借默认值偷偷引入新策略，就会在没有任何提示的情况下改变现有应用的行为。新增字段也不应该一上来就设为必填。

写操作还要考虑重试。请求超时后重试，如果会让同一个操作执行两次，那即使字段和版本都兼容，结果还是不可靠。所以可能产生重复效果的写操作要有幂等性，还要用能识别同一操作的标识。

## 契约难以共存时再加版本号

带版本号的路径能隔离不兼容的契约，但代价是多出好几套要维护、要监控、要退役的接口。

如果可选字段、默认值和未知值都设计清楚了，小规模的增量变更通常可以留在同一个版本里。只有当资源含义、授权模型或操作语义的变化大到一定程度，新旧行为很难在同一个契约里讲清楚怎么共存时，新版本才值得背这些成本。

客户端版本号只是一个比较弱的能力信号。两个构建版本可能属于同一个版本系列，却因为平台、发布批次或配置不同而能力不同。如果功能依赖某种具体行为，显式的能力握手通常比维护一张庞大的版本比较表更清楚。

服务器还是应该记录应用版本，用来诊断问题和判断退役条件。但不能拿客户端自报的版本值去做安全决策。

## 关闭功能时，用户也要有去处

功能开关的好处是：不用等应用更新，就能停掉新行为。但前提是每个活跃客户端在开关打开和关闭两种状态下都能正常工作。

关闭状态要同时定义界面结果和数据行为。举几个例子：

- 如果关掉了写入路径，却让缓存里的控件继续显示，用户只会反复撞上失败；
- 如果移除了响应对象，而旧客户端假定这个对象一定在，应用可能直接崩溃；
- 如果能力不可用，客户端要能显示一个明确的替代状态，而不是继续尝试根本不可能成功的操作。

每个功能开关都应该写清楚：适用对象、默认值、回滚行为、负责人、过期时间和移除条件。一堆永久存在、彼此重叠的开关，会慢慢变成一组没人能完整说清的契约。

服务器控制的开关也替代不了客户端自己的保护。应用仍然要处理能力缺失、操作被拒绝和缓存状态过期这些情况。

## 用剩余流量决定何时退役

我不能只看发布时间或下载量就判断旧客户端已经退出。下载量证明不了实际活跃使用，发布时间也说明不了所有用户都更新了。

服务器记录能看出不同应用版本对各端点的请求情况。测量窗口要足够长，得覆盖那些不常打开应用的用户；用来统计的标识符也要顾及隐私。

只有旧契约的调用方已经消失，或者业务明确决定接受剩余影响时，才能移除它。退役按这个顺序来：

1. 停止创建对旧契约的新依赖；
2. 在适当情况下公布支持边界；
3. 衡量旧路径的剩余流量；
4. 以可控方式拒绝或重定向请求；
5. 确认旧路径不再有流量；
6. 移除服务器端的兼容代码。

客户端这边也要清理不再使用的解析器、功能开关和回退分支。只要它们不再服务任何活跃版本，就应该删掉。没有退役规则的兼容代码，最后会变成永久的歧义。

## 兼容看的是整个过渡期

API 是服务器部署和已安装应用之间的共享状态，任何一方都不能单方面改变自己对它的解释。

后端要提供稳定的语义、兼容的默认值和可以衡量的退役过程。Android 客户端要宽容地解析响应，明确表示未知状态，并提供安全的回退。双方都需要操作标识和可用于诊断的版本信息。

这改变了我评估 API 变更的方式：重点不只是新客户端和新服务器能不能对上，而是过渡期里每一种受支持的组合能不能继续做出正确决定。版本号和功能开关只是工具；真正决定兼容性的，是字段含义、默认行为、能力检查、幂等性，以及有证据支持的退役规则。
