同一个数字经常出现在四个地方：JSON 文件、图、报告和项目页面。

问题出现在我重新运行分析之后。JSON 变了，图也变了，Markdown 里的句子却没有变。经历了足够多次这种偏差后，我不再相信自己能靠记忆让所有副本始终同步。

为了解决这个问题，我做了一个小型证据清单。它把文章中的数字指向机器可读的结果，并检查相关文件是否仍然存在、数值是否仍然满足公开写出的条件。

## 我让文章中的数字可以一路追到源数据

![CFD 主张的证据链](/images/notes/systems/from-cfd-claim-to-auditable-evidence.svg)

我要求文章中的数字能够反向追到机器生成的指标，再追到分析脚本和源数据。截图只能证明某次渲染存在，不能替代这条回溯路径。

现在，我会为每项定量主张记录：

- 一个稳定的 ID；
- 我试图支持的句子；
- JSON 文件及该数值的确切路径；
- 应该通过的比较条件；
- 检查结果所需的文件；
- 生成结果的来源或脚本。

FlowLab 中的一条记录如下：

```json
{
  "id": "u-centerline-rmse",
  "statement": "最细网格的中心线 RMSE 低于顶盖速度的 1%。",
  "metric": {
    "path": "results/validation.json",
    "pointer": "/cases/2/uCenterlineRmse"
  },
  "expectation": { "operator": "<=", "value": 0.01 },
  "artifacts": [
    "results/validation.json",
    "results/centerline-validation.svg"
  ]
}
```

文章仍然可以用自然语言描述结果，但清单会明确告诉我，这句话依赖哪个文件里的哪个数值。

## 我不再把同一个数字复制到 Markdown

如果我直接把 `0.00286` 粘贴到 Markdown 里，就创建了第二个事实来源。分析结果变化后，这个副本不会自动变化。

现在，我改为指向 `/cases/2/uCenterlineRmse`。自动检查可以加载 JSON，找到确切数值，将它与 0.01 比较，并在文件位置或数据结构发生变化时失败。

这不能替我判断 RMSE 是否是合适的指标，也不能判断 1% 是否是合理的门槛。它只能防止同一结果在不同发布位置逐渐变成互相矛盾的数字。

## 我让结果变更自动传到图和文章

我希望一次重新计算能够触发后续检查，而不是让我手工寻找所有受影响的页面。

如果分析脚本改变了 `results.json`，清单中的文件哈希也会改变。依赖该字段的图需要重新生成，引用该图或数字的文章段落需要重新检查。直接覆盖最终 PNG 会切断这条传播路径，所以我不再这样做。

一条更完整的记录可以写成：

```text
claim_id: f1.second_order.cl_bias
value_pointer: results/analysis.json#/numerics/cl_bias_percent
source_artifact: second-order/postProcessing/forceCoeffs
figure: first_order_bias.svg
status: bounded-trend
```

除了数值，我还会记录分母、符号、适用范围和证据状态。这样，我不仅能检查“数字是否相同”，也能看出它是否被放到了原本不适用的场景中。

当不同部分不再一致时，我希望得到明确结果：

| 失配 | 处理方式 |
|---|---|
| Markdown 数字与 JSON 不同 | 构建失败 |
| 图存在但生成输入缺失 | 文件检查失败 |
| 来源文件哈希变化 | 依赖它的主张需要重新检查 |
| 指标通过但用途越界 | 需要人工判断其表述是否真实 |

## 通过检查不等于设计成功

我在 F1 项目中尤其需要这个区别。

其中一项主张指出，2500 万至 3500 万网格单元的生产基线**尚未**完成。记录中的预期值是 `false`。这项检查能够通过，是因为项目页面如实报告了 NO-GO 状态，而不是因为设计取得了成功。

这改变了我对自动检查的看法。它不应该只奖励好结果，而应该检查公开表述是否与证据一致。

因此，失败的网格、被否决的架构或无限区间，只要页面准确描述了结果，也可以通过检查。`PASS` 表示来源链闭合，不表示设计成功；NO-GO、拒绝区间和负面结果同样可以得到一致的检查结果。

## 我不再手工修改发布目录里的图

我以前有一个坏习惯：如果觉得某张图稍微好看一些，就直接在 `public/` 中手工编辑它。这样做虽然快，却让最终图片脱离了生成它的数据和脚本。

现在，对于重要结果，我会把以下内容放在一起：

- 经过最少处理的数据；
- JSON 或 CSV 摘要；
- 生成的图；
- 相关日志；
- 来源标识符；
- 重新生成命令。

自动检查会确认这些文件是否存在、是否仍位于项目内部，以及是否被悄悄替换。项目只有在源结果通过检查后，才会生成用于作品集的发布副本。

我偏好的流程是：

```text
自有输入
  → 分析
  → JSON / CSV 结果
  → 图和报告
  → 主张审计
  → 作品集副本
```

每个项目只需一条命令，就能重复执行这条流程。

## 我已经把它用在自己的作品集上

目前，这套作品集检查覆盖 17 个项目中的 76 项主张和 54 个项目产物。

其中既有成功满足条件的数值，也有我有意记录的否决结果：

- F1 的 NO-GO 陈述能够通过，因为证据确认了这一否决；
- 冷却项目页面能够通过，因为液压数据和温度失效结果与发布文字一致；
- Airfoil Methods 页面能够通过，因为实测值和预测值最终都指向图表所使用的同一组生成表格。

检查范围仍然有限，目前只确认：

- 清单格式正确；
- 指标路径存在；
- 比较结果与记录的结果一致；
- 所需文件存在；
- 重复或格式错误的主张会被拒绝；
- 汇总的 JSON、CSV 和 HTML 可以重新生成。

我有意保持这个范围。求解器和分析脚本不需要理解网站；它们只需要生成结构清楚、能够被后续步骤读取的结果。

## 这套工具不能替我做工程判断

证据清单无法告诉我：

- 某个湍流模型是否合适；
- 某个风洞工况是否真的与我的几何体匹配；
- 某个传感器是否可信；
- NDA 是否允许发布某项内容。

它也无法发现我是否故意没有写下某个重要的负面结果。

这些仍然属于工程判断和诚实表达的问题。这个工具只能让已经公开的主张更容易检查，也更不容易因为复制粘贴而出错。

## 我现在发布数字前会检查五件事

在项目页面上放一个醒目的数字之前，我会先问自己：

1. 一条命令能否重新生成它？
2. 结果是否存储在 JSON 或 CSV 中，而不是只存在于文字里？
3. 这项主张是否指向那个确切的数值？
4. 图和报告是否由同一份数据生成？
5. 如果我重新运行项目后忘记更新页面，检查是否会失败？

这只是一点小结构，不是什么宏大的数据平台。它之所以存在，是因为我知道自己迟早会忘记更新某个手工复制的数字。

对我来说，最大的改进是质疑一个数字的成本变低了。我可以打开对应的记录，沿着指针找到数值，重新运行命令，然后判断那句话是否仍然应该留在页面上。
