同一个数字经常出现在四个地方：JSON 文件、图、报告和项目页面。

问题出在我重新跑分析之后。JSON 变了，图也变了，Markdown 里的句子却没变。这种偏差经历得多了，我就不再相信自己能靠记性让所有副本一直保持一致。

为了解决这个问题，我做了一份数字清单。它把文章里的数字指向机器算出来的结果文件，并且检查相关文件还在不在、数值还满不满足公开写出来的条件。

## 让文章里的数字一路倒查回源数据

![文章里的数字怎么一路倒查回源数据](/images/notes/systems/from-cfd-claim-to-auditable-evidence.svg)

我要求文章里的数字能反着追回去：先追到机器生成的指标，再追到分析脚本和源数据。截图只能证明某张图某次被画出来过，替代不了这条倒查的路。

现在，页面上每个定量结论，我都会记下：

- 一个稳定的 ID；
- 我想支持的那句话；
- JSON 文件，以及那个数值在里面的确切位置；
- 应该通过的比较条件；
- 做检查需要用到哪些文件；
- 结果是谁生成的，来源或脚本是什么。

FlowLab 里的一条记录长这样：

```json
{
  "id": "u-centerline-rmse",
  "statement": "最细网格的中心线 RMSE 低于顶盖速度的 1%。",
  "metric": {
    "path": "results/validation.json",
    "pointer": "/cases/2/uCenterlineRmse"
  },
  "expectation": { "operator": "<=", "value": 0.01 },
  "artifacts": [
    "results/validation.json",
    "results/centerline-validation.svg"
  ]
}
```

文章照样可以用大白话描述结果，但清单会清楚告诉我，这句话靠的是哪个文件里的哪个数值。

## 不再把同一个数字复制进 Markdown

如果我直接把 `0.00286` 粘进 Markdown，就等于造了第二个事实来源。分析结果一变，这个副本不会跟着变。

现在我改成指向 `/cases/2/uCenterlineRmse`。自动检查会加载 JSON，找到那个确切的数值，拿它跟 0.01 比较；文件位置或数据结构一变，检查就会失败。

这不能替我判断 RMSE 是不是合适的指标，也不能判断 1% 是不是合理的门槛。它能做的，只是防止同一个结果在不同发布位置慢慢变成互相矛盾的几个数字。

## 让结果变更传到图和文章

我希望一次重新计算能自动触发后面的检查，而不是靠我手工去找所有受影响的页面。

如果分析脚本改动了 `results.json`，清单里记录的文件哈希也会变。依赖这个字段的图要重新生成，引用了这张图或这个数字的文章段落要重新检查。直接覆盖最终的 PNG 会把这条传递路径切断，所以我不这么干了。

一条更完整的记录可以写成：

```text
claim_id: f1.second_order.cl_bias
value_pointer: results/analysis.json#/numerics/cl_bias_percent
source_artifact: second-order/postProcessing/forceCoeffs
figure: first_order_bias.svg
status: bounded-trend
```

除了数值本身，我还会记下分母、符号、适用范围，以及这个结论目前的状态。这样我不只能检查“数字一不一样”，还能看出它是不是被用到了原本不适用的场景里。

哪些地方对不上，我希望得到明确的处理结果：

| 失配 | 处理方式 |
|---|---|
| Markdown 数字与 JSON 不同 | 构建失败 |
| 图存在但生成输入缺失 | 文件检查失败 |
| 来源文件哈希变化 | 依赖它的结论需要重新检查 |
| 指标通过但用途越界 | 需要人工判断这句话是否真实 |

## 检查通过不等于设计成功

我在 F1 项目里尤其需要分清这个区别。

其中一条结论说，2500 万至 3500 万网格单元的生产基线还没有完成。记录里的预期值是 `false`。这条检查能通过，是因为项目页面如实写出了不通过的状态，而不是因为设计成功了。

这改变了我对自动检查的看法。它不应该只奖励好结果，它应该检查的是：公开写出来的话，和背后的结果对不对得上。

所以，失败的网格、被否决的架构、给不出有限区间的结果，只要页面如实描述了，照样能通过检查。检查通过只说明从页面上的数字能一路倒查回源文件，不说明设计成功；不通过的结论、被否决的区间和负面结果，同样可以得到一致的检查结果。

## 不再手工修改发布目录里的图

我以前有个坏习惯：觉得某张图稍微好看一点，就直接在 `public/` 里手工改它。这样是快，但最终那张图就脱离了生成它的数据和脚本。

现在，对重要的结果，我会把这几样东西放在一起：

- 经过最少处理的数据；
- JSON 或 CSV 摘要；
- 生成的图；
- 相关日志；
- 来源标识符；
- 重新生成的命令。

自动检查会确认这些文件还在不在、还在项目内部，以及有没有被悄悄替换。项目只有在源结果通过检查之后，才会生成给作品集用的发布副本。

我现在的流程是：

```text
自有输入
  → 分析
  → JSON / CSV 结果
  → 图和报告
  → 数字倒查
  → 作品集副本
```

每个项目只需要一条命令，就能把这条流程完整重跑一遍。

## 在作品集上实际检查的范围

目前，这套检查覆盖 17 个项目里的 76 条结论和 54 个结果文件。

里面既有真的满足条件的数值，也有我特意记下来的否决结果：

- F1 的不通过陈述能通过检查，因为背后的记录确认了这次否决；
- 冷却项目页面能通过，因为液压数据和温度失效结果跟发布出来的文字一致；
- Airfoil Methods 页面能通过，因为实测值和预测值最终都指向图表所用的同一组生成表格。

检查的范围仍然有限，目前只确认：

- 清单格式正确；
- 指标路径存在；
- 比较结果和记录的结果一致；
- 需要的文件存在；
- 重复或格式错误的记录会被拒绝；
- 汇总的 JSON、CSV 和 HTML 可以重新生成。

这个范围是我有意保持的。求解器和分析脚本不需要懂这个网站，它们只要生成结构清楚、能被后面的步骤读取的结果就够了。

## 工具替不了工程判断

这份清单没法告诉我：

- 某个湍流模型合不合适；
- 某个风洞工况是不是真的跟我的几何体匹配；
- 某个传感器可不可信；
- NDA 允不允许发布某项内容。

它也没法发现，我是不是故意没写下某个重要的负面结果。

这些仍然是工程判断和诚实表达的问题。这个工具能做的，只是让已经公开的结论更容易检查，也更不容易因为复制粘贴而出错。

## 发布数字前的五项检查

在项目页面上放一个醒目的数字之前，我会先问自己：

1. 一条命令能不能重新生成它？
2. 结果是不是存在 JSON 或 CSV 里，而不是只存在于文字里？
3. 这条结论是不是指向那个确切的数值？
4. 图和报告是不是由同一份数据生成的？
5. 如果我重新跑了项目却忘了更新页面，检查会不会失败？

这套结构并不复杂。它存在的原因很简单：我知道自己迟早会忘记更新某个手工复制的数字。

对我来说，最大的改进是质疑一个数字的成本变低了。我可以打开对应的记录，沿着指针找到数值，重新跑一遍命令，然后判断那句话还应不应该留在页面上。
