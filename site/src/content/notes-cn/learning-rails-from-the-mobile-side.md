在 Android 端调接口的时候，我能看到响应结构、身份认证失败、重试和旧版客户端兼容问题，但看不到这些结果在服务器上是怎样产生的。为了搞懂接口的另一半，我开始用 Ruby on Rails 沿着请求反向追：从路由和控制器出发，经过身份认证、授权和应用规则，一直追到事务与持久化状态。

我的简历上列了 Ruby 和 Ruby on Rails，但没有记录我学习每个概念的时间，也没说明哪些生产系统用过它们。所以这篇笔记只写我从 Rails 里形成的思维模型，不把学习过程写成一段并不存在的项目经历。

## 我先追一条请求要经过哪些边界

![Rails 请求生命周期](/images/notes/systems/learning-rails-from-the-mobile-side.svg)

移动端看到的一个响应，在服务器内部要经过路由、身份判断、应用规则、事务和序列化。如果操作转到了后台，服务器还得把稍后完成的状态重新暴露给客户端。

我把一条创建操作的路径概括成这样：

```text
POST /operations
  → 参数解析与身份
  → 应用规则
  → 数据库事务
  → 版本化响应
  → 可选后台任务状态
```

这个拆分让我看清楚一件事：路由只负责把 HTTP 方法和路径映射到入口。输入适配、授权、事务和响应序列化必须分开，不然数据库字段、业务规则和移动端契约会全部粘在同一个控制器中。

## 为什么我把控制器限制在传输层

Rails 路由为操作命名，把 HTTP 方法和路径连到应用行为上。当同一个资源支持多种操作时，这些约定会直接影响客户端对重试、缓存和失败的判断。

- `GET` 应该读取数据，而不改变持久状态。
- `POST` 通常用于创建内容或启动一项操作。
- `PATCH` 修改现有资源的一部分。
- `DELETE` 删除或停用资源。

问题出在业务决策不断进入控制器之后。这样一来，规则就依赖整个 Web 技术栈，难以单独测试；增加第二个路由时，也容易用另一种方式把同一条规则再实现一遍。

所以我更愿意把控制器当作适配器：HTTP 输入从一侧进来，控制器调用应用规则，再从另一侧输出清晰的应用结果和 HTTP 响应。具体业务决策不应该由控制器自己承担。

## 我怎么用事务重新理解“成功”

在 Android 上，很容易把成功响应看作一次操作的终点。Rails 让我意识到，服务器上的成功还取决于另一件事：持久状态有没有作为一个完整决定发生改变。

假设一项操作需要更新两条记录，并创建一条操作记录。如果第一次更新已经提交，第二次更新随后失败，返回错误并不会自动把之前的状态恢复回去。事务的作用，就是定义一组必须共同成功或共同失败的写入操作。

这也逼着我区分不同的一致性要求：

- 哪些事实必须始终保持一致；
- 哪些状态可以最终一致；
- 两个请求竞争时，哪些规则必须由数据库保护。

应用层验证可以给出更清楚的错误消息，但不能代替数据库对唯一性和引用关系的最终保护。

Rails 能让常见的持久化代码写起来很简洁，但这种简洁也可能隐藏代价。所以我还是要继续查看它在 SQL 层面的结果：查询次数、锁的持续时间、事务范围，以及加载一条记录和逐行加载整个集合之间的差别。

事务成功也只表示持久状态完成了原子改变。移动端仍然需要稳定的操作 ID、明确的失败类型，以及可以查询的后台状态。

## 我为什么把身份认证和授权分开处理

服务器需要先确认是谁发送了请求，再判断这个身份能否执行相应操作。这是两个不同的问题。

身份认证确定的是用户或会话。授权则根据所有权、角色、资源状态和策略，判断某项操作是否允许。用户登录了，也可能没有权限修改某个特定资源。

如果把两者混在一起，服务器容易返回含糊的错误，也可能授予过于宽泛的权限。对 Android 客户端来说，这两种失败需要稳定而不同的结果：

- 会话过期可能触发刷新凭据或重新登录；
- 被禁止的操作在重试后仍然应该被禁止。

如果服务器把两者都返回成同一个通用错误，客户端就只能猜测，甚至可能反复进入身份认证流程。

Rails 过滤器适合统一执行常见的身份认证。针对具体资源的授权决定，则应该放在靠近操作规则的位置，并且能够在不构造浏览器请求的情况下单独测试。

## 序列化是什么：一条兼容性边界

Rails 模型里的信息，通常比移动端响应需要的多。直接返回模型对象，会把数据库字段名、可空细节和内部状态暴露给客户端，也可能公开以后难以删除的字段。

响应序列化器让公开 API 拥有独立结构。即使存储模型改变，序列化器仍可以：

- 保持字段稳定；
- 省略敏感值；
- 明确哪些内容是可选的；
- 检查旧版 Android 客户端能否继续理解响应。

请求方向也需要同样谨慎。请求参数是不可信输入，服务器应该筛选允许接收的字段，验证字段的含义，并在含糊或无效的操作进入持久化层之前拒绝它们。

这个边界让两侧可以按不同节奏演进：数据库服务于当前后端，API 则需要服务于多代客户端。

## 我怎么看待后台任务

有些操作耗时较长，不适合让一个请求一直保持打开。服务器可以先接受任务，返回操作标识符，再在后台完成处理。

但只把工作移到后台并不能解决问题，因为这会改变客户端契约。Android 客户端需要知道操作当前处于哪种状态：

- 正在排队；
- 正在运行；
- 已经完成；
- 已经失败；
- 是否可以安全重试。

如果任务系统只暴露一个长期不变的“处理中”，用户和客户端都无法判断下一步该做什么。

所以任务状态应该持久化，其生命周期应该长于执行任务的工作进程。重试任务需要具备幂等行为，或者使用防护机制避免重复产生影响。失败也必须成为可查询的明确状态，让客户端和支持人员能够检查。

这让我不再把后台任务看作一条脱离请求的线程，而是把它看作另一个需要公开状态转换的状态机。

## Rails 帮我补全了对接口的理解

Android 让我看到后端决策在客户端造成的结果。Rails 则让我把服务器路径拆成具体边界：路由、输入适配、身份认证、授权、应用规则、事务、响应序列化和后台任务状态。

我也看到了几种容易失败的做法：把业务规则塞进控制器、用应用层验证代替数据库约束、混淆身份认证与授权、直接暴露模型，以及启动后台任务却不公开可查询状态。对应的修正都是同一个方向：让每一层只承担清楚、有限的承诺。

Rails 可以快速生成其中许多结构，但真正的工程判断仍然是决定每一层承诺什么。清晰的服务器接口让移动客户端不必靠猜测行动；清晰的客户端状态处理，也能在后端故障演变成用户困惑之前把问题暴露出来。

这套结论的边界同样明确：现有信息只能确认 Ruby 和 Ruby on Rails 属于我的技能列表，不能证明具体学习时间、生产项目经历或使用过的数据库。这里记录的是我形成的技术模型，而不是对未被记录经历的补写。
